## Major Achievement: Fixed PP Deploy Gate Signature Verification

**5+ hour debugging marathon** with Rod to fix Permission Protocol deploy gates. Production deploys were blocked — verify endpoint returned 404 even after approval.

### Bugs Found & Fixed

1. **scopeHash mismatch** (PR #105)
   - Legacy fallback computed hash WITHOUT `scopeType` field
   - New code computed WITH `scopeType`
   - Receipts created with old hash couldn't be found

2. **Missing tenant signing key**
   - `PermissionSigningKey` table only had `global` company row
   - `permission-protocol` company had no key
   - Verification fell back to global, but signature context differed
   - Fix: Copied global key to permission-protocol company via SQL

3. **expiresAt canonicalization bug** (PR #113) — **THE CRITICAL FIX**
   - `signReceipt()` computed `expiresAt = now + config.expirationMs`
   - But `approve/route.ts` stored `requestedExpiresAt` (different value!)
   - Signature computed over one value, DB stored another
   - Verification canonicalized DB value → hash mismatch → SIGNATURE_INVALID
   - Fix: Use `signature.expiresAt` when storing receipt

### Key Debugging Lessons

- **Error masking kills debuggability**: API mapped SIGNATURE_INVALID → RECEIPT_NOT_FOUND → 404. Cost us hours.
- **Canonicalization bugs are brutal**: Any field in SIGNED_FIELDS that differs between sign/verify breaks everything
- **Tenant key provisioning gap**: New companies have no signing key by default
- **Render logs essential**: `[verify] Signature verification mismatch` payload showed keySource, keyFingerprint, resolvedCompanyId

## Evening Session: GitHub Connector Fix + Onboarding Issues

### GitHub Credential Capability Lookup Bug (PR #129)

**Symptom:** Wizard shows "Connected" after token saved, but navigating to GitHub page shows "Not Connected".

**Root Cause:** Capability hierarchy not respected in database query.

When connecting with `repo` scope (write access), credential is stored with `capability: 'write'`.
But `checkConnection()` calls `getGitHubReadToken()` which queries for `capability: 'read'`.
Query used exact match: `capability: capability === 'write' ? { in: ['write', 'admin'] } : capability`.
So for `capability: 'read'`, this became just `capability: 'read'` — no match for `'write'`!

**Fix:** Proper capability hierarchy (higher includes lower):
- `read` → accepts `read`, `write`, or `admin`
- `write` → accepts `write` or `admin`
- `admin` → accepts only `admin`
